# PhysioGhar — Therapist App

A Flutter prototype of the PhysioGhar therapist app. It covers the daily dashboard, the weekly
schedule and availability, booking requests and sessions, patient records with session notes,
profile and language settings, and reporting an issue.

Android only. The data is mocked and kept in memory, so it resets when the app restarts.

## How to run

```bash
flutter pub get
flutter run
```

To build a release APK:

```bash
flutter build apk --release
```

`flutter pub get` also generates the translation files from `lib/l10n/*.arb`. There is no separate
build step to run.

### Running against the API (optional)

There is a companion FastAPI backend. Give the app a base URL at build time and it reads from the
server instead of the mock files:

```bash
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000
```

`10.0.2.2` is how an Android emulator reaches the machine it runs on. Without `API_BASE_URL` the
app uses its mock data. That is the default, and it is what the shipped APK does.

## State-management approach

The app uses Riverpod. The rule it follows is simple: **each piece of data has one owner, and
everything else is worked out from it.**

The owners are:

| Provider | Owns |
|---|---|
| `bookingsProvider` | Every session. |
| `slotsProvider` | Whether each time slot is open or blocked. |
| `availabilityStatusProvider` | The Available / Unavailable switch. |
| `profileProvider` | The therapist's profile. |
| `patientsProvider`, `notesProvider`, `complaintsProvider` | Their own data. |

Nothing else stores this data. Anything that needs it reads from these providers instead of keeping
a copy. Those reads are small providers of their own, for example: today's sessions, the three
dashboard counts, a patient's past sessions, and whether a slot shows as booked.

Two Riverpod types are used. `AsyncNotifier` is for data that has to load, and `Notifier` is for
plain values like the availability switch. Screens use `AsyncValue` to show a spinner while data
loads, an error with a retry button if it fails, and the content when it arrives.

## Project structure

```
lib/
├── main.dart                  starts the app
├── app.dart                   MaterialApp, theme and language
├── l10n/                      app_en.arb, app_ne.arb
├── core/                      shared code, not tied to any feature
│   ├── data/                  mock data loader and the API client
│   ├── format/                date helpers and form validation rules
│   ├── l10n/                  language provider
│   ├── models/                models used by more than one feature
│   ├── router/                routes and the bottom-nav shell
│   ├── theme/                 colours, spacing, text styles
│   └── widgets/               shared widgets
└── features/<feature>/
    ├── model/                 models this feature owns
    ├── providers/             its state and derived values
    ├── repository/            an interface plus a mock and a remote version
    └── presentation/
        ├── screens/
        └── widgets/
```

Each feature holds everything it needs: its models, its mock data, its repository, its providers
and its screens. `core/` only holds things that more than one feature uses.

Screens contain no rules. They read providers and call methods on them.

## Assumptions

The brief left some things open. Where it did, the simplest sensible option was chosen.

1. A slot is 60 minutes. Adding a slot is refused if it overlaps an existing one at all, not only
   when the start time is the same.
2. Slots are created for this week and the next seven days. The schedule screen shows this week, as
   the brief asks. Rescheduling can move a session to any day in that range.
3. Remarks added when completing a session belong to the session. They appear on the session and in
   the patient's history. They are not patient notes, which are separate.
4. A note has a required note field, plus optional exercises and a plan for next time. Exercises are
   typed one per line.
5. A patient's last session date and past sessions come from their completed sessions, so finishing
   a session updates the patient record straight away.
6. There is no login. Logging out asks for confirmation, puts the data back to its starting state
   and returns to the dashboard.
7. Nepali covers the tab labels, the dashboard headings and the account screens. The brief says a
   full translation is not needed.
8. Complaint reference numbers are made in the app, in the format `PG-#####`.
9. Pressing back on any tab other than Home returns to Home. Only Home closes the app.

# Short explanation

## Why the state is organised this way

Riverpod was set by the brief, so the real decision was how to use it.

The problem in this app is that the same facts appear in several places. Today's sessions show on
the dashboard. The same sessions make time slots look booked on the schedule. The same sessions
form a patient's history. If each screen kept its own copy, they would disagree as soon as anything
changed, and every action would need code to update three or four other screens.

So sessions are stored once, and everything else is worked out from them. Accepting a booking
changes one list. The dashboard count, the slot on the schedule and the patient's history all
update by themselves, because they were reading from that list the whole time.

That is why there is no refresh or sync code anywhere in the app. It also removes a whole class of
bug: a session and its slot cannot disagree, because the slot's booked state is not stored at all.

## How the mock data is handled

The mock files live in `assets/mock/`, one per feature. They are read through a `MockDataSource`,
which sits behind a repository for each feature. Every repository is an interface with a mock
version, so nothing above it knows where the data came from. That is what let the API version be
added later without changing a single screen.

Two things were done on purpose:

- **Dates are stored relative to today**, as "3 days from now, at 14:00", and turned into real dates
  when the data loads. So the sample data from the brief always lands on today, whenever the app is
  opened.
- **Slots are built from a per-weekday pattern** rather than fixed dates, so the week always looks
  realistic: a blocked lunch hour each day, shorter weekends.

Loading waits 300–600 ms on purpose, so the loading states are real rather than decoration. Actions
the therapist takes apply immediately and confirm with a message.

## Important decisions

- **A slot does not store whether it is booked.** It only knows if it is open or blocked. Booked is
  worked out by checking the time against the sessions. A session and its slot can never disagree.
- **Double booking is blocked in one place.** Accepting or rescheduling checks that a slot exists at
  that time, is not blocked, and is not already taken. If any of that fails, the action is refused
  with a message saying what to do instead.
- **Pending requests do not hold a slot.** This is what makes a real clash possible. The sample data
  includes two requests at the same time and one on a blocked slot, so both refusals can be seen by
  tapping rather than only existing in theory.
- **A session carries the patient's name as well as their id**, the way an API response would. This
  keeps the bookings code independent of the patients code.
- **One session detail screen.** Which buttons it shows depends on the session's status.
- **Declined and cancelled are told apart.** Both sit under Cancelled, but a declined request says
  "Declined".

## What I would improve with more time

- **Saving data.** Everything is in memory, so it resets on restart. A local database would fix
  that, and the repository layer is already the place to add it.
- **Writing to the API.** The repositories only read. In API mode the app reads from the server but
  still changes data in memory, so accepting a booking does not reach the server. Adding the write
  calls to the repository interfaces is the next step; the API already supports them.
- **More Nepali.** Only part of the app is translated. The rest of the text should move into the
  translation files, along with Nepali date formatting.
- **Search and filters** on the patient list and the bookings tabs, which would matter well before a
  real caseload.
- **Accessibility.** Labels for the icon-only buttons, and a pass with a screen reader.
- **Better schedule editing**, such as dragging a session to a new time, or setting weekly working
  hours once instead of editing each day.
